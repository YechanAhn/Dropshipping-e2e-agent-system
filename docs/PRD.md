# DropAgent PRD (Product Requirements Document)
## 드롭쉬핑 E2E 자동화 에이전트 시스템

## 1. Gemini 제안 기술스택 비판적 검토

### 1.1 에이전트 프레임워크: CrewAI 또는 LangGraph

**Gemini 제안의 문제점:**

"CrewAI 또는 LangGraph"라고 병렬 제안한 것 자체가 두 프레임워크의 본질적 차이를 이해하지 못한 결과다. 이 둘은 대체재가 아니라 성격이 전혀 다른 도구다.

| 구분 | CrewAI | LangGraph |
|------|--------|-----------|
| 추상화 수준 | 고수준 (역할 기반) | 저수준 (그래프 기반) |
| 상태 관리 | Task output 기반, 네이티브 체크포인팅 없음 | 명시적 상태 그래프, 시간여행 디버깅 |
| 조건 분기 | 제한적 | 네이티브 조건부 엣지, 사이클 지원 |
| 프로덕션 안정성 | 디버깅 어려움, 로깅 문제 | API 안정성 보장 |

**비판:**

드롭쉬핑 시스템은 "소싱 → 콘텐츠 생성 → 등록 → 주문 감시 → CS"라는 **명확한 상태 전이와 조건 분기**가 필요한 워크플로우다. 예를 들어 "상품 등록 실패 시 재시도 → 3회 실패 시 스킵 후 알림" 같은 로직은 그래프 기반 상태 머신이 훨씬 자연스럽다.

CrewAI의 "역할 기반 협업"은 브레인스토밍이나 연구 태스크에는 적합하지만, 정해진 비즈니스 프로세스를 정확히 실행해야 하는 경우에는 **과도한 자율성이 오히려 리스크**다.

**최종 판단:**

> LangGraph를 채택하되, LLM이 불필요한 결정론적 구간은 일반 Python 함수로 구현하고, LLM이 필요한 노드만 에이전트로 구성하는 **하이브리드 접근**이 최적.

추가 고려:
- **MCP (Model Context Protocol) + LangGraph 조합**: MCP가 업계 표준화됨. LangGraph 노드 내에서 MCP 서버를 통해 외부 도구(네이버 API, 알리 API)를 표준화된 방식으로 연결하면 확장성 극대화
- **순수 Python 워크플로우 엔진 고려**: LLM이 필요한 구간(콘텐츠 생성, 번역)은 한정적이고, 나머지는 결정론적 비즈니스 로직이므로 Temporal/Prefect 같은 엔진도 검토 가치 있음

### 1.2 LLM: Claude 3.5 Sonnet

**문제점:**

- Claude 3.5 Sonnet은 **이미 레거시**. 현재 최신: Claude Opus 4.5, Claude Sonnet 4, Claude Haiku 3.5
- 모든 태스크에 동일 모델 사용은 **비용 대비 효율이 극히 낮음**

**최종 판단: 태스크별 모델 라우팅**

| 태스크 | 권장 모델 | 이유 |
|--------|-----------|------|
| 상품 설명 생성/번역 | Claude Sonnet 4 | 품질/비용 균형 최적 |
| 마진율 분석 판단 | Claude Sonnet 4 | 구조화된 추론 |
| 카테고리 매칭 | Claude Haiku 3.5 | 단순 분류, 비용 절감 |
| 키워드 추출 | Claude Haiku 3.5 | 속도 우선 |
| 이미지 분석 | Claude Sonnet 4 | 멀티모달 지원 |

> 반복적이고 패턴화된 작업은 LLM 호출 결과를 캐싱하고, 데이터가 쌓이면 경량 분류 모델(scikit-learn)로 대체하는 전략으로 비용을 극적으로 줄인다.

### 1.3 DB: Supabase 또는 PostgreSQL

**문제점:**

"또는"으로 병렬 제안한 것이 문제. **Supabase IS PostgreSQL.** Supabase는 PostgreSQL 위에 인증/실시간/REST API를 올린 BaaS 플랫폼이지 별도 DB가 아니다.

| 관점 | Supabase (호스팅) | Self-hosted PostgreSQL |
|------|-------------------|----------------------|
| 초기 세팅 | 수 분 | 프로덕션 수준 2-4주 |
| 비용 (유사 스펙) | ~$410/월 | ~$50/월 (Hetzner VPS) |
| 운영 부담 | 낮음 | 높음 |
| 실시간 기능 | 내장 | 별도 구현 필요 |

**최종 판단:**

> - Phase 1-2: **Supabase 호스팅** → 빠른 개발 속도
> - Phase 3+: **Self-hosted PostgreSQL + TimescaleDB** → 시계열 데이터 최적화, 비용 절감

**심각한 누락: Redis**

> Gemini 제안에 **Redis가 빠진 것은 치명적**. 네이버 API 응답 캐싱, 알리 가격 캐싱, Rate Limit 관리에 Redis는 필수.

### 1.4 브라우저 자동화: Playwright

**문제점:**

Playwright는 안티봇 탐지에 기본 상태로 취약. `__playwright__binding__` 등 윈도우 객체 변수를 노출하며 CDP 기반 탐지에도 걸린다. 알리익스프레스는 Cloudflare + 자체 안티봇을 운영하므로 **빠르게 차단될 가능성 높음**.

| 도구 | 안티봇 우회 | 안정성 | 비동기 |
|------|------------|--------|--------|
| Playwright (기본) | 낮음 | 높음 | 있음 |
| Patchright (패치) | 중간 | 중간 | 있음 |
| nodriver | 높음 | 중간 | 네이티브 |

**최종 판단: 다층 전략**

> 1. **1차: 공식 API** → 알리 Affiliate API로 가능한 데이터 최대한 확보
> 2. **2차: nodriver** → API로 불가능한 데이터 수집
> 3. **3차: 서드파티** → Apify, ScrapFly를 fallback으로
> 4. **네이버 측은 공식 API만** → 법적 대응 리스크 회피

### 1.5 메시징: Slack SDK / Discord Webhook

**문제점:**

한국 사업자 대상 시스템에서 **Slack/Discord를 1순위 제안한 것은 맥락에 맞지 않음.** 한국 이커머스 셀러의 메시징 생태계는 카카오톡/텔레그램 중심.

**최종 판단:**

| 우선순위 | 채널 | 이유 |
|---------|------|------|
| 1순위 | **텔레그램 Bot API** | 무료, 봇 API 완성도 높음, 셀러 커뮤니티에서 가장 많이 사용 |
| 2순위 | 카카오톡 알림톡 | 가장 자연스러움, 단 건당 8-15원 비용 |
| 3순위 | Slack Webhook | 기술팀 내부 모니터링/디버깅용으로만 |

### 1.6 대시보드: Streamlit / Retool

**문제점:**

Streamlit의 프로덕션 한계가 명확하다:
- 모든 사용자 입력 시 **전체 페이지 리로드**
- 사용자당 Python 쓰레드 점유 → **RAM 선형 증가**
- 멀티페이지 구조 제한적, 진정한 라우팅 없음
- 백엔드 레이어 없음 → REST API, 백그라운드 잡 별도 구성 필요

이 시스템의 대시보드는 상품 목록 필터링(수천 건), 마진율 차트, 실시간 주문 모니터링, 에이전트 로그, 설정 변경 등 **본격적인 웹 애플리케이션**이 필요하며 Streamlit 설계 목적과 맞지 않는다.

**최종 판단:**

> - Phase 1: **Streamlit** → MVP 검증 단계 프로토타입
> - Phase 4: **FastAPI (백엔드) + Reflex (프론트)** → Python만으로 풀스택 구축

### 1.7 인프라: Docker + AWS EC2 / VPS

**문제점:**

네이버 커머스 API는 **IP 등록 필요, 최대 3개**. AWS EC2 비용 구조가 이 프로젝트 규모에 과도.

| 인프라 | 월 비용 | 고정 IP | 관리 부담 |
|--------|---------|---------|----------|
| AWS EC2 t3.medium | ~$30-60+ | Elastic IP | 중간 |
| Hetzner VPS CX32 | ~$7-15 | 포함 | 낮음 |
| Oracle Cloud Free | 무료 | 포함 | 낮음 |

**최종 판단:**

> - 초기: **Hetzner VPS** 또는 Oracle Cloud Free Tier (고정 IP, 비용 최소화)
> - Phase 3+: Docker Compose로 단일 서버 내 컨테이너화
> - **AWS는 과도** — MSA가 아니며 단일 서버에서 충분. IAM/VPC 오버헤드 불필요

### 1.8 에이전트 구조: 3개 에이전트

**문제점:**

3개 분류가 **너무 거칠다.** "소싱 에이전트"가 데이터 수집, 가격 분석, 마진 계산, 우선순위를 모두 담당하면 단일 책임 원칙 위반.

**최종 판단: 5+1 에이전트**

```
[오케스트레이터]
    ├── [데이터 수집 에이전트] : 알리 크롤링, 네이버 가격/트렌드 수집
    ├── [분석 에이전트]       : 마진율 계산, 판매량 추정, 우선순위 스코어링
    ├── [콘텐츠 에이전트]     : 번역, SEO 최적화, 상세페이지 생성
    ├── [등록 에이전트]       : 네이버 커머스 API 상품 등록/수정/삭제
    ├── [주문/CS 에이전트]    : 주문 감시, 알리 자동 주문, 배송 추적
    └── [모니터링 에이전트]   : 헬스체크, 에러 알림, 성능 메트릭
```

시스템 Cron은 Python 통합 어렵고 에러 핸들링/재시도/태스크 의존성 관리 불가.

| 가격 변동 감시 | 3시간 | 알리 API |
| 시스템 헬스체크 | 1분 | 내부 |

## 2. 알리-네이버 마진율 빅데이터 분석 기능 실현 가능성

### 2.1 핵심 도전: 두 플랫폼의 공통 키가 없다

알리 상품과 네이버 상품 사이에 공통 식별자(UPC, EAN)가 대부분 없다. 이것이 가장 근본적인 난관.

| 데이터 소스 | 확보 가능 데이터 | 확보 방법 | 제한 |
|------------|----------------|----------|------|
| 알리 Affiliate API | 상품명, 가격, 할인율, 이미지, 카테고리 | 공식 API | 일 5,000건 |
| 알리 웹 | 판매량, 리뷰 수, 평점, 배송비 | nodriver | 안티봇 리스크 |
| 네이버 쇼핑 검색 API | 상품명, 가격, 판매처, 브랜드 | 공식 API | 일 25,000건 |
| 네이버 데이터랩 | 카테고리 클릭 추이 (상대값), TOP 500 키워드 | 공식 API | 절대값 미제공 |
| 네이버 쇼핑파트너센터 | 자사 상품 노출수/클릭수 (절대값) | 로그인 후 조회 | 자사만 |
| 서드파티 (아이템스카우트 등) | 경쟁사 추정 판매량 | API/스크래핑 | 유료, 정확도 미보장 |

### 2.2 마진율 계산 알고리즘

```
마진율 = (네이버 판매 예상가 - 총 원가) / 네이버 판매 예상가 × 100

총 원가 = 알리 상품가
        + 알리 배송비
        + 환율 마진 (5%)
        + 네이버 수수료 (카테고리별 5.5~11%)
        + CS 리스크 비용 (3%)
        + 환불/반품 비용 (2%)

네이버 판매 예상가 = 네이버 쇼핑 검색 API 동일/유사 상품 기준
```

**네이버 판매 예상가 산정 방법:**

1. 네이버 쇼핑 검색 API로 유사 상품 검색 (상품명 키워드 기반)
2. 상위 10개 결과의 가격 분포 분석
3. 중앙값 또는 25~50 백분위수를 "경쟁력 있는 가격"으로 설정
4. 목표 마진율(예: 30%)을 역산하여 소싱 가격 상한선 도출

### 2.3 판매량 추정 (핵심 난관)

네이버 데이터랩이 절대 판매량을 제공하지 않으므로 간접 추정 필요.

**다층 추정 모델:**

```
추정_판매량 = f(클릭 추이 상대값, 키워드 검색량, 카테고리 경쟁도, 리뷰 수 증가율)
```

1. **클릭 추이 프록시**: 데이터랩 상대 비율을 자사 상품 실제 클릭수와 교차 검증
2. **리뷰 수 프록시**: 네이버 쇼핑 검색 API에서 리뷰 수 주기적 추적 (구매자의 3-10%가 리뷰 작성)
3. **키워드 검색량**: 검색광고 API 월간 검색량 + 데이터랩 트렌드
4. **카테고리 경쟁도**: 동일 키워드 상품 수 대비 검색량 비율

### 2.4 우선순위 스코어링 공식

```python
priority_score = (
    w1 * margin_rate_normalized       # 마진율 (0~1), 가중치 0.35
    + w2 * demand_score_normalized    # 수요 점수 (0~1), 가중치 0.25
    + w3 * competition_score_inv      # 경쟁도 역수 (0~1), 가중치 0.15
    + w4 * review_growth_normalized   # 리뷰 증가율 (0~1), 가중치 0.15
    + w5 * supplier_reliability       # 공급자 신뢰도 (0~1), 가중치 0.10
)

# 초기 가중치 (실험적 조정)
w1, w2, w3, w4, w5 = 0.35, 0.25, 0.15, 0.15, 0.10
```

### 2.5 실현 가능성 판정

| 기능 | 판정 | 비고 |
|------|------|------|
| 마진율 계산 | **실현 가능** | 알리 API + 네이버 쇼핑 검색 API 조합으로 즉시 가능 |
| 판매량 추정 | **부분적 실현 가능** | ±30% 오차 예상, 상대적 순위는 유의미 |
| 자동 우선순위 | **실현 가능** | 다중 팩터 스코어링으로 구현 |
| "빅데이터 분석" | **과장된 표현** | 현실적으로는 "다중 소스 데이터 기반 휴리스틱 스코어링" |

## 3. 제품 개요

| 항목 | 내용 |
|------|------|
| **제품명** | DropAgent — 드롭쉬핑 E2E 자동화 에이전트 시스템 |
| **목적** | 알리익스프레스 상품을 네이버 스마트스토어에 자동 소싱/분석/등록/운영하는 풀사이클 자동화 |
| **핵심 가치** | "높은 마진 + 검증된 수요"의 상품을 데이터 기반으로 자동 발굴, 수작업 대비 10배+ 효율 |
| **주요 사용자** | 네이버 스마트스토어 드롭쉬핑 셀러 (1인~소규모 팀) |
| **범위** | 상품 소싱 → 마진 분석 → 콘텐츠 생성 → 스토어 등록 → 주문 처리 → CS 지원 |

## 4. 핵심 기능 요구사항

### FR-001: 상품 소싱 및 데이터 수집
- 알리익스프레스 Affiliate API를 통한 상품 검색 및 데이터 수집
- 카테고리별, 키워드별 상품 탐색
- 상품 상세 정보 수집 (가격, 배송비, 평점, 주문 수, 셀러 정보)
- 수집 데이터의 DB 저장 및 이력 관리

### FR-002: 네이버 시장 데이터 수집
- 네이버 쇼핑 검색 API를 통한 동종 상품 가격 조사
- 네이버 데이터랩 쇼핑인사이트 API를 통한 카테고리 트렌드 수집
- 키워드별 검색량 및 경쟁도 데이터 수집
- 수집 데이터의 시계열 저장

### FR-003: 마진율 분석 및 우선순위 스코어링
- 실시간 환율 반영 원가 계산
- 카테고리별 네이버 수수료 자동 반영
- 다중 팩터 우선순위 스코어링
- 가중치 사용자 조정 가능
- 분석 결과 대시보드 시각화

### FR-004: 콘텐츠 자동 생성
- LLM 기반 상품명 번역 및 SEO 최적화
- 상세 설명 자동 생성 (네이버 가이드라인 준수)
- 이미지 다운로드 및 최적화
- 카테고리 자동 매칭 (알리 → 네이버)

### FR-005: 스마트스토어 상품 등록
- 네이버 커머스 API를 통한 자동 등록
- Rate Limit 준수 (초당 2회, Token Bucket)
- 등록 실패 시 지수 백오프 재시도
- 등록 상태 추적 및 알림

### FR-006: 주문 관리 및 자동 처리

- 주문 상태 동기화 (알리 ↔ 네이버)

### FR-007: CS 지원
- 고객 문의 자동 분류 (배송/교환/환불/일반)

### FR-008: 알림 및 모니터링

## 8. 최종 기술스택 (Gemini vs 최종)

| 영역 | Gemini 제안 | 최종 권장 | 이유 |
|------|------------|----------|------|
| 에이전트 | CrewAI 또는 LangGraph | **LangGraph + MCP** | 상태 관리, 조건 분기, 안정성 |
| LLM | Claude 3.5 Sonnet | **Sonnet 4 + Haiku 3.5 (라우팅)** | 태스크별 비용 최적화 |
| DB | Supabase 또는 PostgreSQL | **Supabase → PostgreSQL+TimescaleDB** | 단계적 진화 |
| 캐시 | (없음) | **Redis** | API 캐싱, Rate Limit, 큐 |
| 브라우저 | Playwright | **nodriver + 공식 API 우선** | 안티봇 우회 |
| 메시징 | Slack/Discord | **텔레그램 Bot API** | 한국 셀러 생태계 |
| 대시보드 | Streamlit/Retool | **Streamlit → Reflex** | 점진적 고도화 |
| API 서버 | (없음) | **FastAPI** | 비동기, Pydantic |
| 인프라 | Docker + AWS EC2 | **Docker + Hetzner VPS** | 비용, 고정 IP |
| 스케줄러 | Cron Job | **APScheduler + Redis** | Python 통합, 재시도 |
| HTTP | (미지정) | **httpx (async)** | 비동기 병렬화 |
| ORM | (미지정) | **SQLAlchemy 2.0 + Alembic** | 비동기, 마이그레이션 |
| 로깅 | (미지정) | **structlog** | 구조화 로깅 |
| 패키지 | (미지정) | **uv** | 빠른 의존성 해결 |
| 테스트 | (미지정) | **pytest + pytest-asyncio** | 비동기 테스트 |
